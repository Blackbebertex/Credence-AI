# CredenceAI-Gov P0 application audit

**Assessment date:** 2026-10-11  
**Assessment type:** Preliminary source/configuration audit of the current checkout; not a certification, penetration test, legal opinion, or production readiness approval.  
**Scope:** Repository source, tests, migrations, Docker Compose, CI workflow, and project documentation. Synthetic-only local P0 assumed from the project documents. No production system, cloud account, identity provider, real evidence, or external service was accessed.

## 1. Executive summary

The checkout is a proposed synthetic-data-only P0, but it contains runnable API and security-related scaffolding whose behavior is weaker than its names and comments imply. The strongest risks are a known fallback JWT signing secret, missing object-level case authorization, unbounded/unvalidated upload handling, malware scanning that fails open, a worker that maps arbitrary decoded text to `supported`, and signed packages that do not bind artifact bytes to the signed manifest. These issues would be High severity if the endpoints/utilities were exposed or used for evidence workflows. Their present likelihood is reduced by the documented local-only status and lack of deployment evidence; that status is not independently verified.

The initial audit identified 12 findings. A follow-up remediation pass changed the authentication boundary, endpoint authorization, upload validation, scanner error handling, evidence-state fallback, package integrity, and CORS policy. The full available suite now passes: **61 passed** under Python 3.14.8, and `python -m compileall -q backend` passes. This is not a security test result. The project metadata requires Python 3.12+, and no dependency lockfile is present, so this execution does not establish supported-runtime compatibility or reproducibility. Changes were made surgically while retaining the pre-existing edits.

**Release position:** Keep this synthetic-only. The fixes reduce several local risks, but production use remains blocked by the HS256 development auth stub (no Keycloak JWKS integration), lack of actual sandbox and malware-scanner wiring into intake, in-memory API persistence, incomplete database/RLS integration, and unresolved owner/counsel/security decisions.

### Detailed findings

#### F-01 — Known fallback JWT secret and tokens need not expire

- **Evidence:** `backend/credence_gov/auth.py:9-10` sets a literal fallback secret and uses HS256. `:25-43` creates tokens without an expiry claim. `:58-68` decodes using that same fallback and requires `sub`, `tenant_id`, `aud`, `iss`, but not `exp`.
- **Impact:** Anyone who can reach the API and knows the source fallback can mint tokens for arbitrary users/tenants/roles unless runtime configuration replaces the key. Tokens without expiration can remain valid indefinitely. The realm config uses OIDC but this code does not validate Keycloak signatures/JWKS.
- **Recommendation:** Remove the fallback; fail application startup outside a dedicated test/dev mode if a secret or OIDC issuer/JWKS configuration is absent. In deployment, validate asymmetric issuer keys, issuer, audience, `exp`, `nbf`, and allowed algorithms; never trust client-provided role/tenant claims without issuer validation. Add explicit test-only token helper boundaries.
- **Verification:** Startup fails closed with missing auth config; forged HS256/dev-key token rejected in production-mode configuration; missing/expired/not-yet-valid tokens rejected; issuer/audience mismatch denied.
- **Residual:** Real IdP integration and MFA assurance require staging federation tests.

#### F-02 — Case artifact upload checks tenant only, not case-level access or role

- **Evidence:** `backend/credence_gov/api.py:105-123` creates cases for any authenticated principal. `:126-137` accepts uploads after checking only that `case["tenant_id"] == user.tenant_id`; it does not require owner, a case grant, or an allowed role. All authenticated roles therefore reach the operation.
- **Impact:** A user in the same tenant can upload to another user's case. This is a broken object-level/function-level authorization condition (OWASP API1/API5); it undermines evidence ownership and may enable contamination of records. Cross-tenant upload is blocked in this in-memory path, but broader tenant isolation is not proven.
- **Recommendation:** Define a deny-by-default role/action matrix and case-access service (owner/grant/supervisor rules). Enforce both authorization checks for every case/artifact endpoint; keep tenant from verified identity only. Return a consistent non-enumerating not-found/forbidden policy.
- **Verification:** Automated matrix tests across analyst/reviewer/supervisor/admin/auditor/service, case owner/non-owner, same/cross tenant; unauthorized operations cause no storage or database side effect.

#### F-03 — Upload is unbounded, mislabeled Base64 is stored literally, MIME/type are trusted

- **Evidence:** `backend/credence_gov/api.py:74-77` accepts an unbounded string and documents it as “Base64 or UTF-8”; `:138` UTF-8 encodes it rather than decoding/validating Base64. `:139-145` stores caller-provided MIME and artifact type without checking content signature or configured size.
- **Impact:** Large request bodies can consume memory/storage; malformed content may be stored under false metadata and later passed to parsers/scanners. Hashes then describe the encoded text, not the intended original file. No upload limit is enforced by this endpoint.
- **Recommendation:** Set proxy and application body limits; make input contract unambiguous (prefer multipart streaming or strict Base64 decode with validation); cap decoded bytes; validate allowed type against magic bytes and parser constraints; reject empty/mismatched input; quarantine, scan, then preserve original and record custody. Do not trust MIME from request.
- **Verification:** Oversize, invalid Base64, empty, type mismatch, and malformed file cases are rejected before storage; accepted bytes/hash match exactly; memory behavior is bounded under configured limit.

#### F-04 — ClamAV outage/error is reported as clean

- **Evidence:** `backend/credence_gov/antivirus.py:36-39` returns clean for empty input. `:66-80` catches connection errors and falls through to a clean result at `:84-89`, describing only an internal EICAR substring check as a “heuristic safety scanner.” Unexpected daemon responses also fall through to clean.
- **Impact:** Scanning is fail-open. Malware can be marked safe when ClamAV is unavailable or responds unexpectedly. The function's `is_safe` property then allows that result to be treated as accepted.
- **Recommendation:** Treat empty/malformed input and scanner unavailability as ERROR/unknown and block analysis; only return clean after a successful complete daemon scan. Add timeouts/size caps and a separately managed quarantine path. Avoid claims of clean based on a single test signature.
- **Verification:** Daemon unavailable, timeout, malformed response, and partial response all fail closed; only explicit daemon `OK` after full stream returns clean; EICAR fixture returns infected.

#### F-05 — Arbitrary decoded text becomes `supported`; no sandbox is implemented

- **Evidence:** `backend/credence_gov/tasks.py:76-84` decodes every byte sequence as UTF-8 with replacement and sets evidence state to `supported` whenever resulting text is nonempty. The class is named `SandboxedAnalysisWorker`, but the method performs direct in-process decoding and has no process/container isolation, resource limits, or parser controls.
- **Impact:** Untrusted content is presented as support without evidence comparison, citations, source validation, or analyzer provenance. Binary data can also become replacement text. This conflicts with the advisory evidence-state requirements and risks automation bias. The name/comment overstates implemented isolation.
- **Recommendation:** Until a validated analyzer exists, return `insufficient_evidence`/`not_analyzed` for all content; separate extraction status from policy evidence state. Do not call this sandboxed. Before parsing, use isolated workers with no egress, bounded CPU/memory/time, strict formats, and versioned output provenance.
- **Verification:** Arbitrary nonempty and binary files never yield supported; state transitions require validated finding inputs and rule version; worker isolation/ejection limits verified in an integration environment.

#### F-06 — Signed package does not bind artifact bytes; archive paths are caller-controlled

- **Evidence:** `backend/credence_gov/package_builder.py:42-55` copies caller-supplied names and hashes into the manifest and signs only that manifest. `:84` writes artifact bytes under `artifacts/{name}` without recomputing/comparing the supplied hash or sanitizing the name. Audit events are written into the ZIP (`:67-70`) but the signed manifest contains only their count (`:53`).
- **Impact:** A verifier that checks only the signature can accept substituted artifact bytes because the signed hash was not verified against those bytes by the builder; the signed manifest also does not commit to the audit-trail bytes. Names containing traversal components can create unsafe ZIP entries for downstream extractors. The current code does not show a package verifier contract.
- **Recommendation:** Canonicalize and validate archive paths; reject absolute paths, `..`, duplicate names, and control characters. Compute hashes from bytes and reject mismatches. Manifest must include all payload digests, including audit/findings files, and define canonical serialization and public-key/key-id handling. Add an independent verifier that rejects any mismatch.
- **Verification:** Altering any archived member, audit event, manifest, or signature fails verification; path traversal names are rejected; valid packages round-trip against a documented schema.

#### F-07 — RLS migration omits per-case records and API does not use database persistence

- **Evidence:** `backend/migrations/versions/0002_row_level_security.py:18` lists only `cases`, `artifacts`, `users`. Models define `audit_events`, `policy_decisions`, and `review_tasks` keyed by `case_id` but not protected by RLS. API endpoints in `backend/credence_gov/api.py:94-103` store cases in `_DB_CASES`; artifact metadata uses `_DB_ARTIFACTS` and local in-memory storage (`:91-92`), with no DB session or tenant transaction context.
- **Impact:** The migration is not a complete tenant boundary for per-case records. More broadly, database controls do not protect these API routes because current handlers do not use that database. A future connection can create false assurance if the RLS migration is treated as complete.
- **Recommendation:** Before persistence integration, define tenant-aware relational constraints (including composite case/tenant consistency), apply RLS to all tenant-scoped tables or prove an alternative, set tenant context transaction-locally from verified identity, and use a non-owner/non-bypass runtime DB role. Connect API operations and audit writes to that persistence layer.
- **Verification:** PostgreSQL integration tests with runtime role prove missing tenant returns zero rows and cross-tenant select/insert/update/delete fail for every tenant-scoped table; migration tests verify policies and referential consistency.

#### F-08 — CORS allows every origin with credentials

- **Evidence:** `backend/credence_gov/app.py:18-22` configures `allow_origins=["*"]`, `allow_credentials=True`, and wildcard methods/headers.
- **Impact:** If browser credentials are used, an untrusted origin may be allowed to make credentialed requests depending on middleware behavior and browser enforcement. This expands the attack surface for cookie-based or ambient-credential sessions.
- **Recommendation:** Use explicit environment-specific trusted origins; allow only necessary methods/headers. If the API is bearer-token-only, disable credentialed CORS unless a documented use case requires it.
- **Verification:** Preflight/actual CORS responses allow only the configured origins and deny an attacker-controlled origin; production config rejects wildcard-plus-credentials.

#### F-09 — Hash chain is not externally anchored and appends can fork

- **Evidence:** `backend/credence_gov/audit.py` computes plain SHA-256 links with no keyed signature or external checkpoint. `record_event_to_db` selects latest by `recorded_at` and random ID, then appends (`:91-109`); model timestamps are application-generated. Concurrent transactions can read the same head. A database writer able to rewrite the table can recompute the full chain.
- **Impact:** The chain can detect accidental/simple edits but does not provide tamper resistance against privileged database modification, and concurrent append order can become ambiguous or produce a broken chain. Documentation should not imply immutable/auditable custody from this alone.
- **Recommendation:** Serialize append per case using database locking/sequence semantics; define deterministic ordering. Protect checkpoints with a signing key controlled outside the database or an approved append-only store. Document the threat model and verification procedure.
- **Verification:** Concurrent append stress test yields one valid ordered chain; mutation/rewrite tests demonstrate the protection boundary and signature/checkpoint verification.

#### F-10 — BSA generator emits statutory attestation language without verifying its basis

- **Evidence:** `backend/credence_gov/bsa_certificate.py:42-61` accepts free-form deponent, department, device identifier, hashes, and chain head, then creates “hereby certify under Section 63” text stating secure-system/ordinary-operation assertions. No evidence or signer authorization is checked in this function. No API route was observed.
- **Impact:** If used operationally, the output could imply facts or legal sufficiency not established by the software. Project docs explicitly say counsel confirmation is required and no legal sufficiency is claimed.
- **Recommendation:** Keep disabled/deferred until counsel approves the certificate format, process, signer authority, and evidence requirements. Replace assertion-generation with a reviewed template requiring authenticated signer workflow and verifiable source records; label output draft until approved.
- **Verification:** Counsel-approved template and role-controlled signing workflow; tests reject missing/unverified provenance and unauthorized signers. Legal review is not replaceable by technical tests.

#### F-11 — CI does not run code tests or supply-chain security checks

- **Evidence:** `.github/workflows/ci.yml:14-22` checks only that five files exist. There are no test, dependency, secret, container, or SBOM jobs. `pyproject.toml` has no lockfile and `docs/DEPENDENCIES.md` calls pins/digests pending.
- **Impact:** A green CI run says nothing about code correctness or vulnerabilities; dependencies and images are not reproducibly resolved or scanned. This is acceptable only as an explicitly named documentation-foundation workflow.
- **Recommendation:** Keep foundation job label accurate; add pinned supported Python setup, tests, lint/type checks as adopted, dependency lock and audit, secret scanning, image digest/provenance checks, and SBOM generation before release. Define severity-based blocking rules.
- **Verification:** CI visibly runs the required checks on PR and fails on seeded test failure, known policy-violating dependency, leaked test secret, or unpinned release image.

#### F-12 — API state is process-local and API writes no audit event

- **Evidence:** API case/artifact dictionaries and `LocalStorageAdapter` are module globals (`api.py:91-92`); the adapter stores values in an in-memory dictionary (`storage_adapter.py:39-40`). Case and upload handlers do not call `AuditLedger`.
- **Impact:** A restart loses all cases and artifacts. Multiple workers have independent state. Uploaded evidence lacks the planned custody/audit event, so the storage metadata is not a durable evidence record.
- **Recommendation:** Treat these routes as test-only until persistence is implemented. Use transactional metadata/audit writes and durable object storage with verified immutability semantics; do not claim custody completion until all required steps succeed atomically or are reconciled.
- **Verification:** Restart and multi-process tests preserve/retrieve records; failed audit/object writes leave no falsely accepted artifact; custody event references exact content digest.

7. **Tenant controls/migrations**: no change; add composite tenant/case integrity, RLS coverage, transaction-local tenant context, and DB integration tests under least-privilege runtime role after architecture decision.
